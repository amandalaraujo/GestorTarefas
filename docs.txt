Sistema de Gestão de Riscos & Compliance (GRC Lite)
Este projeto simula um painel interno onde uma empresa cadastra Riscos, mapeia Ações Preventivas e faz a verificação através de um Checklist de Conformidade.

O que vai no projeto em 1 final de semana (MVP 90% pronto):

Backend (C# / .NET Core API):

CRUD completo de Riscos (Descrição, Categoria, Nível de Impacto: Baixo/Médio/Alto, Status: Ativo/Mitigado).

CRUD de Ações/Checklists vinculados a cada risco (Ex: "Realizar backup quinzenal").

Endpoint para atualizar o status do checklist (Ex: Pendente/Concluído).

Banco de Dados (SQL Server ou Oracle Local / SQLite para testes):

Tabelas bem estruturadas (Riscos e AcoesCompliance) com relacionamentos (1 para N).

Frontend Básico:

Interface simples em Razor Pages, Blazor ou React/HTML+JS consumindo a API.

Tela de dashboard simples mostrando lista de riscos e progresso dos checklists.

Versionamento & Documentação (Foco na Vaga):

Repositório no GitHub organizadinho com commits frequentes.

Um arquivo README.md completo detalhando o problema de negócio, como rodar o projeto localmente e o checklist de testes aplicados.

O que o comando dotnet new webapi faz no fundo?
Ele gera uma estrutura inicial de arquivos. As três partes principais que você precisa entender agora são:

Program.cs (O Cérebro): É o ponto de entrada da aplicação. É aqui que o servidor é configurado, as rotas são registradas e o Swagger é ativado para o modo de desenvolvimento.

Controllers/ (As Portas de Entrada): É a pasta onde ficam as classes de controle. Cada Controller é responsável por receber as requisições HTTP (GET, POST, PUT, DELETE) e devolver respostas em formato JSON.

appsettings.json (Configurações): Arquivo onde guardamos variáveis de ambiente, como a linha de conexão com o banco de dados (connection string).

Como o Swagger entra nessa história?
O Swagger (OpenAPI) é uma ferramenta visual que funciona como um menu interativo da sua API.

Documentação Automática: Ele lê o seu código C# e identifica quais rotas/endpoints você criou.

Testes Sem Frontend: Em vez de você precisar criar uma tela HTML/CSS logo no início só para ver se o código funciona, o Swagger gera uma página web onde você clica em botões para disparar requisições para a sua API e ver os dados retornando do banco em tempo real.

O Fluxo Completo de Comunicação
Para ter uma visão clara de como as coisas se conectam:

[ Navegador / Swagger / Front-end ]

** ARQUIVO MODEL ** 

1. Primeiro: o que é esse namespace?
namespace GestorTarefas.API.Models
{
    ...
}

Pense no namespace como uma forma de organizar e agrupar classes.

No seu projeto:

GestorTarefas.API
│
├── Models
│   └── Tarefa.cs
│
├── Controllers
│
├── Data
│
└── Program.cs

O namespace:

GestorTarefas.API.Models

indica que as classes daquele arquivo pertencem ao grupo Models da aplicação.

É parecido com a ideia de organização por módulos/pacotes que você encontra em outras linguagens.

2. class Tarefa é realmente o "molde"

Aqui sua comparação com C++ faz bastante sentido:

public class Tarefa
{
    ...
}

Você está dizendo:

"Uma Tarefa, dentro do meu sistema, terá essas características."

Por exemplo:

public int Id { get; set; }
public string Titulo { get; set; }
public string? Descricao { get; set; }

Uma tarefa poderia ser representada assim:

Tarefa
├── Id: 1
├── Titulo: "Estudar C#"
├── Descricao: "Estudar classes e interfaces"
├── Prioridade: Alta
├── Status: EmAndamento
├── DataCriacao: ...
└── DataConclusaoPrevista: ...

Então sim: você está definindo a estrutura dos objetos Tarefa.

Mas tem uma diferença em relação ao seu exemplo de .hpp + .cpp.

3. Não é exatamente como .hpp + .cpp

No C++ você poderia ter:

// Tarefa.hpp

class Tarefa {
    int id;
    string titulo;

    void concluir();
};

e depois:

// Tarefa.cpp

void Tarefa::concluir() {
    ...
}

No C# normalmente não existe essa separação obrigatória entre declaração e implementação.

Você poderia colocar:

public class Tarefa
{
    public int Id { get; set; }

    public string Titulo { get; set; }

    public void Concluir()
    {
        // lógica
    }
}

Tudo na mesma classe.

Só que nesse projeto específico, estamos usando Tarefa principalmente como uma entidade de dados/modelo, não como uma classe cheia de comportamentos.

4. E aqui entra o Django

Essa é a comparação mais importante.

No Django você provavelmente faria algo como:

class Tarefa(models.Model):
    titulo = models.CharField(max_length=200)
    descricao = models.TextField(null=True)
    prioridade = models.IntegerField(...)
    status = models.IntegerField(...)
    data_criacao = models.DateTimeField(auto_now_add=True)

No C# + Entity Framework, você pode pensar aproximadamente assim:

public class Tarefa
{
    public int Id { get; set; }
    public string Titulo { get; set; }
    public string? Descricao { get; set; }
    public PrioridadeEnum Prioridade { get; set; }
    public StatusEnum Status { get; set; }
    public DateTime DataCriacao { get; set; }
}

Ou seja:

Django

Model
   ↓
define estrutura dos dados
   ↓
ORM
   ↓
Banco

ASP.NET + Entity Framework

Classe C#
   ↓
define estrutura dos dados
   ↓
Entity Framework (ORM)
   ↓
Banco

Então sua percepção de que isso é um Model está correta.

5. Agora vamos ao string?

Essa parte:

public string? Descricao { get; set; }

é muito importante no C# moderno.

O ? significa que aquela variável pode receber null.

Então:

string Titulo

significa, considerando nullable reference types habilitado:

Titulo não deveria ser null.

Enquanto:

string? Descricao

significa:

Descricao pode ser null.

Por exemplo:

Tarefa tarefa = new Tarefa();

tarefa.Titulo = "Estudar C#";
tarefa.Descricao = null;

Isso é válido porque Descricao foi definida como:

string?
Por que descrição pode ser null?

Porque talvez o usuário crie:

Título: Estudar C#
Descrição: [vazio]

Não existe problema.

Mas você provavelmente quer que toda tarefa tenha um título:

Título: ❌ vazio

Então:

public string Titulo { get; set; }

representa um campo obrigatório, enquanto:

public string? Descricao { get; set; }

representa um campo opcional.

Importante

? aqui não significa simplesmente "opcional" em qualquer situação.

Ele está indicando nulabilidade.

No caso de string?, significa que a referência pode ser null.

6. O que são { get; set; }?

Essa é outra coisa que provavelmente vai parecer estranha para quem vem de C++.

Quando você escreve:

public int Id { get; set; }

você está criando uma propriedade.

Simplificando bastante, pense:

public int Id { get; set; }

como:

"Essa classe possui uma propriedade chamada Id, que pode ser lida e alterada."

Por exemplo:

tarefa.Id = 10;

Console.WriteLine(tarefa.Id);

get → permite obter o valor.

set → permite alterar o valor.

7. E esse = string.Empty?

Aqui:

public string Titulo { get; set; } = string.Empty;

estamos inicializando Titulo com uma string vazia:

""

em vez de deixar a propriedade sem valor.

Então inicialmente:

Titulo = ""

Depois:

tarefa.Titulo = "Estudar C#";

passa a ser:

Titulo = "Estudar C#"
8. Agora os enum

Você criou:

public enum PrioridadeEnum
{
    Baixa = 1,
    Normal = 2,
    Alta = 3
}

Isso cria um tipo específico chamado PrioridadeEnum.

Ele só possui aquelas opções:

Baixa
Normal
Alta

Então:

public PrioridadeEnum Prioridade { get; set; }

significa:

A propriedade Prioridade deve utilizar uma das opções de PrioridadeEnum.

Por exemplo:

tarefa.Prioridade = PrioridadeEnum.Alta;
E por que Alta = 3?

Porque internamente o enum possui valores numéricos:

Baixa       → 1
Normal      → 2
Alta        → 3

Você poderia ter:

PrioridadeEnum.Alta

e internamente o valor correspondente seria:

3

Isso será particularmente útil quando o Entity Framework trabalhar com o banco.

9. O mesmo acontece com Status
public enum StatusEnum
{
    Pendente = 1,
    EmAndamento = 2,
    Concluida = 3
}

Então:

public StatusEnum Status { get; set; } = StatusEnum.Pendente;

significa:

Toda nova tarefa começa, por padrão, com status Pendente.

Então se você fizer:

Tarefa tarefa = new Tarefa();

ela já terá:

Status = Pendente

sem você precisar definir manualmente.

10. Essa parte é a data de criação
public DateTime DataCriacao { get; set; } = DateTime.Now;

Aqui:

DateTime

é o tipo usado para representar data + horário.

E:

DateTime.Now

pega a data/hora atual da máquina.

Então quando uma nova tarefa é criada:

Tarefa tarefa = new Tarefa();

ela recebe automaticamente algo como:

DataCriacao = 17/09/2026 19:05
11. E por que DateTime? aqui?

Temos:

public DateTime? DataConclusaoPrevista { get; set; }

Perceba o ? novamente.

Isso significa:

A data de conclusão prevista pode existir ou não.

Por exemplo:

Tarefa:
    Título: Estudar C#
    DataConclusaoPrevista: 20/09/2026

ou:

Tarefa:
    Título: Estudar C#
    DataConclusaoPrevista: null

Porque talvez o usuário ainda não tenha definido um prazo.

12. Agora chegamos à parte mais interessante: Checklist

Você tem:

public List<ItemChecklist> Checklist { get; set; } = new();

Isso significa:

Uma Tarefa possui uma lista de ItemChecklist.

Imagine:

Tarefa
"Estudar C#"

Checklist
├── Estudar classes       ☑
├── Estudar interfaces    ☑
├── Estudar EF Core       ☐
└── Criar API             ☐

Cada item da lista é um objeto ItemChecklist.

Por isso:

List<ItemChecklist>

significa:

uma lista contendo objetos do tipo ItemChecklist.

13. E o = new()?

Aqui:

public List<ItemChecklist> Checklist { get; set; } = new();

estamos criando uma lista vazia inicialmente.

É como começar com:

Checklist = []

Depois você pode adicionar:

tarefa.Checklist.Add(item);
14. E quem é ItemChecklist?

É outra classe:

public class ItemChecklist
{
    public int Id { get; set; }
    public string Descricao { get; set; } = string.Empty;
    public bool Concluido { get; set; } = false;
    public int TarefaId { get; set; }
}

Ela representa um item individual do checklist.

Por exemplo:

ItemChecklist

Id: 1
Descricao: "Estudar Entity Framework"
Concluido: false
TarefaId: 5
15. bool Concluido

Aqui é simples:

public bool Concluido { get; set; } = false;

bool só pode ser:

true
false

Então:

Concluido = false

→ ainda não terminou.

Concluido = true

→ terminou.

16. E finalmente TarefaId

Essa propriedade:

public int TarefaId { get; set; }

é muito importante para o banco de dados.

Imagine:

Tarefa
ID = 10
Título = "Estudar C#"

E temos:

Checklist

ID   Descrição                 TarefaId
1    Estudar classes             10
2    Estudar EF Core             10
3    Criar API                   10

O:

TarefaId = 10

fala:

"Este item de checklist pertence à tarefa de ID 10."

Isso é uma chave estrangeira (foreign key).

17. A estrutura completa na cabeça

Eu pensaria nesse Model assim:

                    TAREFA
                      │
       ┌──────────────┼──────────────┐
       │              │              │
      Id           Titulo         Descricao
       │
       ├── Prioridade
       │      ├── Baixa
       │      ├── Normal
       │      └── Alta
       │
       ├── Status
       │      ├── Pendente
       │      ├── EmAndamento
       │      └── Concluida
       │
       ├── DataCriacao
       │
       ├── DataConclusaoPrevista
       │
       └── Checklist
              │
              ├── ItemChecklist
              │     ├── Id
              │     ├── Descricao
              │     ├── Concluido
              │     └── TarefaId
              │
              ├── ItemChecklist
              └── ItemChecklist

E o relacionamento no banco tende a ficar:

TAREFA
-------------------------
Id (PK)
Titulo
Descricao
Prioridade
Status
DataCriacao
DataConclusaoPrevista


          1
          │
          │
          │
          N
ITEM_CHECKLIST
-------------------------
Id (PK)
Descricao
Concluido
TarefaId (FK)

Ou seja:

1 Tarefa → N Itens de Checklist

Uma tarefa pode ter vários itens.
